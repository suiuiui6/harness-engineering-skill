## Harness Engineering 不是七层清单，是三层推进弧

如果你只能记住一件事，记住这个：**七层是"地图"，三层推进弧是"路线"**。七层告诉你有什么东西要管，三层推进弧告诉你什么时候管、以什么顺序管、管到什么程度算过关。

---

### 推进主线：三层弧，而非七层平铺

```
第一弧：Foundation & Capability Proof（基础与能力验证）
  → 问题：这东西真的能跑通吗？
  → 做法：单组件 MVP，环境隔离，用运行时事实说话
  → 出口条件：一个孤立但完整的最小能力证明

第二弧：Engineering Loop（工程化循环）
  → 问题：这东西能扛得住迭代和组合吗？
  → 做法：渐进集成，桥接测试，熵值轮换
  → 出口条件：组件在组合中稳定，反馈能闭环

第三弧：Productization（产品化）
  → 问题：这东西能交付给外部使用吗？
  → 做法：契约固化、运维边界、退出与重入协议
  → 出口条件：可交付、可接手、可退役
```

七层在这三条弧上逐步展开，而不是一次性全部拉满。**第一弧可能只涉及 2-3 层，第三弧才把七层完整覆盖**。这就是它和"七层清单式框架"的根本区别——用力顺序不同。

---

### 核心哲学：三条硬约束

**1. 运行时事实 > 静态文档。**
不要对着设计文档论证能力存在——跑起来，抓日志，拿证据。API 实际返回什么，比 API 文档里承诺什么更重要。

**2. 单组件 MVP 先于系统集成。**
不要一上来就搭全套 bridge 和 pipeline。先把一个组件在隔离环境里从头到尾跑通，再逐步接上相邻组件。环境隔离不是"额外开销"，是**防止假阳性验证**的核心机制。

**3. 渐进集成，不是大爆炸上线。**
每接一个组件就验证一次，每次验证都回到第一弧的出口条件。你在第三弧发现的任何问题，都要回溯到第一弧重新确认——**下游崩了，根大概率在上游**。

---

### 一句话总结

> Harness Engineering 不是"做到七层就完了"，而是"先证明最小能力存在，再在组合中迭代加固，最后收缩为可交付产品"。七层是度量尺，三层弧是推进逻辑——清单告诉你站在哪里，弧告诉你下一步该往哪走。
