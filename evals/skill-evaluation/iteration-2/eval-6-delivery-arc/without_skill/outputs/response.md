## 一句话定调

> **Harness Engineering 不是"七个步骤打勾"，而是一条从"这个东西到底能做什么"走到"这个东西可以安全交付"的完整研发控制链路。七层只是它的执行契约——推进主线和核心哲学才是它的灵魂。**

---

## 推进主线：三段交付弧（Delivery Arc）

把七层重新映射到三个阶段，就能看清这条线到底在推什么：

### 第一阶段：基础与能力验证（Foundation and Capability Proof）

**回答的问题：我们面对的东西，真实的能力边界在哪？**

这一步的核心动作不是写代码，而是**建立可观测的执行面**（workbench baseline），然后用源代码或 API 的实测证据画出每个组件的"能做什么"和"不能做什么"（Layer 0），再在隔离环境里独立跑通每个组件的最简路径（Layer 1）。

关键判断标准：**任何"应该支持"但没有证据的断言，就是失败信号。**

这个阶段的价值在于——很多人直接跳到"怎么集成"，但 Harness Engineering 要求你先证明"你真的知道这些组件各自能干什么"。这是所有后续工程决策的事实根基。

### 第二阶段：工程收敛循环（Engineering Loop）

**回答的问题：怎么把这些已验证的能力，组织成一个可工程化、可桥接、可架构的系统？**

这里从 Layer 1 的组件实测契约出发，逐层向上收敛：

- **Layer 2**：定义组件间的依赖拓扑和桥接管线，每个阶段必须有显式的输入/输出 schema
- **Layer 3**：验证外部工具兼容性，产出技术架构文档和决策理由
- **Layer 4**：写 PRD → 写后端 API 规格 → 写前端系统规格（严格按依赖顺序），交叉验证一致性

核心驱动力：**规格不是"想要什么"的产物，而是"实测行为"的固化。** 任何时刻运行时事实和文档不一致，要么写回文档，要么回退修正。

### 第三阶段：产品化落地（Productization）

**回答的问题：怎么把这个系统安全地交出去，而不是"跑过一次就算完"？**

- **Layer 5**：定义工程治理规则——仓库边界、运行时隔离、密钥管理、依赖锁定、Product Contract（含变更日志和验收标准）
- **Layer 6**：按蓝图实现、集成测试、关闭 bug 循环、关闭 review 循环、执行生产就绪检查清单

关键判断标准：**"跑过一次"不算完成。必须所有测试在真实依赖上通过、运行时和静态问题全部关闭、生产就绪清单全部通过，才算交付。**

## 核心哲学：六个锚点

这六条不是贴在墙上的口号，而是嵌入在每一层 gate 判断里的硬约束：

### 1. 证据优先，无证据不行进

> "No pass evidence, no forward movement."

这是整个方法论的第一原则。每一层的 pass gate 必须有可追溯的证据指针（日志、测试结果、检查记录），缺证据就是失败。**"代码看起来能跑"不替代证据。**

### 2. 源码/API 实测是最终权威

> "Source or API inspection and runtime facts outrank assumptions, plans, and stale documents."

文档说支持某个功能？不算。运行时事实不支持？以运行时为准。这个优先级规则贯穿所有决策——它防止团队在错误假设上建一整栋楼。

### 3. 分层分解，最小回退

> "Layered decomposition: reopen only the smallest valid layer."

失败时不要默认回到 Layer 0 重来。先找到**第一个失效的上游假设**，回退到刚好能修复它的那一层，然后从那里重新验证下游。这避免了每次出问题就"推倒重来"的工程灾难。

### 4. 先证单件，再架桥梁

> "Single-component MVP proof before bridge integration."

每个组件必须在隔离环境中独立跑通最简路径，才能进入集成。**集成在组件隔离验证通过之前就开始，是一个显式的失败信号。** 这杜绝了共享运行时带来的非确定性污染。

### 5. 规格固化于实测行为

> "Spec solidification from measured behavior, not hopes."

Layer 1 的组件规格不是"设计文档"，而是从实测输出中推导出来的 I/O 契约。上下游的规格一致性不是靠 review 会议保证，而是靠交叉验证硬检查。

### 6. 交付完成由制品定义，不由"代码跑通"定义

> "Missing artifacts or missing evidence means the layer is not complete, even when code appears to run."

每个执行周期必须留下：每层的 gate 状态、证据指针、回退决策记录、受影响规格的更新、以及包含 `scope_result` 和 `operation_state` 的关闭记录。缺一个就算未完成。

## 为什么它不是单纯的七层清单

你可以用一句话给团队讲清楚区别：

| 清单思维 | Harness Engineering |
|---|---|
| 七步做完就结束 | 两层失败就回退，修完再前进 |
| 一个模式走到底 | Bootstrap 和 Maintenance 两种执行路径，切换有明确合约 |
| 失败靠人判断怎么办 | 每层有预设的 fail signal + rollback target rule |
| "跑通了"算完成 | 证据、制品、关闭记录缺一不可 |
| 文档写了就不管了 | 运行时事实反向写回文档，写不回就回退 |

**一个清单告诉你能做什么。一套方法论告诉你在什么条件下前进、什么条件下后退、什么时候算真正结束。**

推进主线让你看清"从哪到哪"，核心哲学让你理解"为什么这么走"，七层合约是执行的抓手，三段交付弧是叙事的地图。三样东西合在一起，才是 Harness Engineering 的完整面貌。
